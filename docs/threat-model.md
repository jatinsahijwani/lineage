# Lineage — Threat Model

## Trust Assumptions

| Component | Trust Level | Notes |
|-----------|-------------|-------|
| 0G Chain (EVM) | Full | Smart contract correctness is our primary security surface |
| 0G Storage | Storage integrity | Content-addressed; we verify roots on-chain |
| 0G DA | Availability | Receipts posted; we trust DA that the bytes are available |
| TEE (0G Compute) | Conditional | v1 mock mode: no TEE. Production: trust the TEE hardware |
| Operator (settler) | Semi-trusted | Controls batch timing; cannot forge Merkle roots without TEE sigs |
| iNFT owners | Untrusted | May set adversarial weights; bounded by invariants below |

---

## Threat Categories

### T1: Weight Manipulation at Mint

**Threat:** A creator mints a ModelINFT with weights that don't reflect the true contribution of parent DataINFTs (e.g., claiming 100% ownerSplitBps to keep all royalties).

**Mitigation:** v1 makes no claim that declared weights are accurate — they are self-reported. The `weightBps` invariant (must sum to 10000 per node) ensures internal consistency, but accuracy is a social/market problem. v2 Shapley would address this.

**Residual risk:** Creators can lie about relative contributions. Downstream users should inspect the lineage graph before trusting a model.

---

### T2: Cycle Injection

**Threat:** An attacker tries to create a cycle in the lineage graph (A→B→A) to cause infinite loops in the settler's DFS propagation.

**Mitigation:** `LineageRegistry._isAcyclic()` runs a depth-bounded DFS from every proposed parent before recording any edge. If a path from any parent reaches the new child, the transaction reverts. Max depth is 32 — beyond that, registration also fails.

**Residual risk:** Very deep (but acyclic) graphs near depth 32 will fail to register. This is an explicit design tradeoff.

---

### T3: Receipt Replay

**Threat:** An attacker submits the same attribution receipt twice to the settler, causing double-payment.

**Mitigation:** `AttributionVerifier._usedReceipts` tracks every receipt ID. `markReceiptUsed()` reverts if the ID was already marked, and is called by `RoyaltySplitter.postBatch()` for every receipt in a batch. Receipt IDs are UUIDs generated by the TEE.

**Residual risk:** In mock TEE mode, the runner generates UUIDs with `crypto.randomUUID()`. Collision probability is negligible (2^122 space). In production, the TEE generates the receipt ID deterministically from `(inputDigest, outputDigest, computeNodeId, timestamp)`.

---

### T4: Forged Receipts

**Threat:** An attacker forges a receipt claiming attribution for a model they don't control, to redirect royalties.

**Mitigation:** `AttributionVerifier.verifyReceipt()` recovers the signer from an ECDSA signature over the CBOR-encoded receipt. The recovered address must match the `teePublicKey` registered at deployment. Only 0G Compute TEE nodes with the correct hardware key can produce valid signatures.

**Residual risk:** If the TEE key is compromised, receipts can be forged. This is the core trust assumption of all TEE-based systems.

---

### T5: Double Claim

**Threat:** A contributor calls `claim()` twice with the same valid Merkle proof.

**Mitigation:** `RoyaltySplitter` tracks `claimed[batchId][recipient][token]`. A second call with the same `(batchId, recipient, token)` reverts.

**Residual risk:** None under correct EVM semantics.

---

### T6: Operator Withholding Batches

**Threat:** The operator (settler) refuses to post batches, preventing contributors from claiming royalties.

**Mitigation:** v1 is centralized — there is one operator (the deployer). The operator cannot steal funds (they can only post valid Merkle roots), but they can delay settlement. The DAO/governance upgrade path in the roadmap addresses this via a decentralized operator set.

**Residual risk:** v1 has a single operator. Contributors must trust the protocol team to run the settler honestly. This is disclosed in v1 scope.

---

### T7: Royalty Policy Rug

**Threat:** A model creator updates `RoyaltyPolicy` (e.g., changes `ownerSplitBps` to 10000) right before a large inference batch settles, capturing all royalties.

**Mitigation:** `updateRoyaltyPolicy()` has a 24-hour timelock. The pending update is recorded on-chain; it cannot be applied until `block.timestamp >= pendingEffectiveAt`. This gives data/skill contributors a 24-hour window to react (e.g., refuse further inferences).

**Residual risk:** A 24-hour timelock may be too short for some use cases. v2 may increase this or add per-update notifications.

---

### T8: Front-running Merkle Proofs

**Threat:** An attacker observes a pending `claim()` transaction in the mempool, extracts the Merkle proof, and front-runs with their own claim.

**Mitigation:** The Merkle leaf encodes `(batchId, recipient, token, amount)`. A proof for Alice's `recipient` address will fail when submitted with Bob's address. Front-running is impossible without control of the recipient address.

---

## What Is NOT Protected in v1

- **Sybil resistance for iNFT creators:** Anyone can mint DataINFTs claiming any dataset. No verification of provenance.
- **Data quality:** DataINFT contents are not validated. A junk dataset and a real dataset look identical on-chain.
- **Model accuracy:** No on-chain verification that a ModelINFT's weights match the declared training data.
- **Decentralized operator:** The settler is a single trusted process in v1.
- **Key management for data decryption:** The libsodium key is held off-chain by the data owner. If lost, encrypted artifacts are unrecoverable.

These are explicitly listed in `README.md §14` as v1 cuts.
